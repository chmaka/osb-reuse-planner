# Architecture (Phase 0)

**Frontend:** Vite, React, TypeScript; UI state in React. Responsive SVG editor. **Storage:** Dexie IndexedDB schema v1 for remnants, original image Blobs, parts and audit events; no sync. **Math:** pure TS polygon/segment functions; all coordinates millimeters. **Worker:** off-main-thread grid placement with exact polygon containment/collision validation in geometry.ts. **Export:** a reference-only ASCII AC1015 DXF writer, never a production toolpath. **PWA:** service worker caches app assets for offline startup.

Planned: calibrated multi-marker projective transform, optical segmentation, polygon repair/holes, verified stock state machine, real irregular nesting optimizer and DXF parser round-trip. No Rust crate yet: WASM benefit and integration not proven.

### Acquisition additions (Phase 1)
Camera/format handling lives in `src/features/camera/`; file upload is always available. The source Blob is stored separately from its EXIF-normalized preview Blob. Scan metadata and recoverable CAPTURED records are stored by a forward-only Dexie v2 migration. One quality worker processes downsampled pixel buffers and returns warnings, not camera accuracy or production verification. Heavy HEIC conversion loads on demand; it is never a compulsory prerequisite to opening the app.

### Phase 2 planar metrology
The 4-corner homography `src/features/calibration/homography.ts` maps EXIF-oriented image pixel coordinates to millimeters using a numerically normalized 8×8 linear solve. It runs entirely in the browser. The detected ArUco marker's four corners form a planar reference of known printed physical size; `aruco.worker.ts` performs pixel detection off-main-thread, while `aruco.ts` lazily prepares the image and printable marker. The photo is **not** lens-undistorted; only the polygon coordinates are perspective-corrected. No physical gauge acceptance is inferred from exact 4-point reprojection because four correspondences fit exactly by construction. User selects another independent length to evaluate transformed distances, but even a passing software check cannot prove CNC accuracy. 

### Phase 3 segmentation & geometric inspection
`src/features/segmentation/segment.ts` implements deterministic, dependency-free browser image segmentation. `run.ts` creates a 720px (max edge) image with EXIF-oriented coordinates and transfers RGBA to a dedicated worker. Color distance to a median corner/background estimate yields a binary mask; 3×3 majority denoising and largest connected component eliminate isolated noise, with boundary loops traced and simplified into polygon suggestions. Their original image-pixel coordinates are transformed by the same phase-2 canonical scale or homography as manually traced contours. Auto-detected holes are only proposals until explicitly accepted. Outer contour, holes and defects are editable separate rings. Strict geometry validation prohibits invalid, overlapping or outside exclusions; usable area subtracts holes/defects. Original image is retained, CNC status never changes automatically. These boundaries are pixel-level approximations; they are not manufacturing toolpaths.

### Phase 4 Re:bble adaptation
Re:bble's original Python SAM2/OpenCV implementation is not bundled. We implement its marker-offset foreground prompts in `features/segmentation/rebble.ts` and reuse validated perspective geometry from Phase 2. `SamModel` and `AutoProcessor` from Transformers.js v3.8.1 load lazily on WebGPU only when the AI option is selected. `Xenova/slimsam-77-uniform` (not SAM2) is a separate model that may need network download. The component extracts a predicted mask and converts it to rings by the existing deterministic trace/simplification utilities. The contrast mode is still the default on mobile due to cost and WebGPU variability. The marker must lie on the source OSB plane; specular glare, shadows, false holes and extrapolation all risk inaccuracy. The app never uses remote inference services or transmits source photographs through its own code.

### Phase 5 QA data and metrics
The pure metrics module features/validation/metrics.ts computes checks only from explicit operator-provided physical measurements. PilotValidation.tsx displays offline controls and exports. Dexie schema v3 adds a validation table whose records snapshot digital dimensions and originating remnant revision, preserving historical evidence when geometry changes. The app never changes a remnant to VERIFIED because a pair of dimensions passed an arbitrary internal threshold. Export CSV/JSON is local, no sync. Summary statistics combine outer bounding width and height error only, NOT local contour edge accuracy.

### Phase 5.2 local geometry evidence
`src/features/validation/edge-check.ts` is a pure module for selecting two existing vertices of the **same polygon ring** and computing direct Euclidean separation in mm. `LocalEdgeValidation.tsx` renders a vector contour and A/B touch/dropdown selection. New Dexie v4 table `edgeChecks` snapshots the original vertices and remnant revision with manually entered physical ground truth. Audit events are appended atomically; no remnant mutation occurs. Summary errors for these checks remain separate from width/height pilot errors. CSV/JSON are local downloads, not uploads. Neither metric proves full edge profile accuracy.

### Phase 5.3 versioned local backup
`features/backup/archive.ts`: pure JSON+Base64 container serialization, image SHA-256 and structured record integrity, size and referential validation. `features/backup/storage.ts`: consistent Dexie read snapshot, collision preflight and atomic seven-table merge. `features/backup/SettingsBackup.tsx`: explicit export/preview/restore UI with conflicts and user approval, no remote service. JSON carries all existing data including source photography, physically measured width/height and vertex spans; no automatic verification or CNC status changes. Unencrypted by design; keep archives privately.
